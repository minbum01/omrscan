# 대용량 배치(1000장급) 처리 성능 개선 기획 (2026-07-08)

> **상태**: 분석 완료(2차) · 구현 대기
> **관련 파일**: `js/batch.js`, `js/imageManager.js`, `js/scoring.js`, `js/correction.js`, `js/canvas.js`

---

## 증상

사용자 보고:
1. "1000장 가까이 되는걸 한꺼번에 넣으면 omr이 항상 부하가 많이 생기더라고"
2. "결과표에서도 천장에 대해서 해서그런지 결과표창도 매우느리고"
3. "교정탭에서 시간이 매우 오래걸리는데 이 문제가 정말 심각해" — **가장 심각한 것으로 재확인**

계기: 전모 6회차 OMR 스캔본(언어 962장 / 추리 961장)을 한 세션에 업로드해 일괄분석하려는 상황.

이번 2차 분석 목적: "1000장을 한 번에 다 처리할 수 있는가?"에 답하기 위해 교정탭까지 포함해서 점검. 결론부터: **원인 A만 고치면 오히려 교정탭이 지금보다 더 느려진다.** 아래 원인 C·D를 반드시 같이 봐야 한다.

## 원인 A — 일괄분석 중 이미지 메모리가 해제되지 않음

### 정상 동작 (열람 시)
`imageManager.js`의 `_MAX_LOADED = 3` + `_evictDistantImages()`는 사용자가 이미지 목록에서 다른 장을 **선택(select)**할 때만 작동한다. 현재 선택 위치 기준 앞뒤 3장만 `imgElement`(디코딩된 원본 비트맵)를 메모리에 남기고 나머지는 해제한다.

### 문제
`BatchProcess.run()` (`batch.js:152~338`)의 `processNext()`는 이미지를 순차적으로 처리하면서:
```js
if (typeof ImageManager !== 'undefined' && (!imgObj.imgElement || ...)) {
    const loaded = await ImageManager.ensureLoaded(imgObj); // 다시 로드
}
...
imgObj.rois.forEach(roi => { ... }); // 분석
```
분석이 끝난 뒤 **해당 이미지의 `imgElement`를 다시 해제하지 않는다.** `_evictDistantImages`는 batch 루프 안에서 전혀 호출되지 않는다.

### 규모 추정
실제 스캔본 샘플 확인 결과 원본 해상도 **3300×2550px**. `ImageManager.MAX_SIZE=2000`으로 리사이즈되어도 약 2000×1550px → 디코딩 비트맵 약 **12MB/장**.

- 962장을 한 세션에 일괄분석 → 배치 막바지에는 처리 완료된 962장의 비트맵이 모두 메모리에 남아 **약 11GB** 누적

### 중요 — 현재 상태에서는 오히려 "다행"인 부분
업로드 직후 `handleUpload()`가 `select(0)`을 호출해 `_evictDistantImages`가 이미지 대부분을 한 차례 해제하지만, 이후 `Batch.run()`은 처리한 이미지를 다시 로드한 뒤 **한 번도 해제하지 않으므로**, 배치가 끝난 시점에는 결과적으로 거의 모든 이미지가 다시 메모리에 로드된 상태로 남는다.

→ 즉 지금은 "배치 도중 메모리가 계속 쌓이는 문제"이면서, 동시에 "배치가 끝나고 나면 대부분의 이미지가 로드돼 있어서 교정탭이 이미지를 다시 읽어올 필요가 없는" 상태이기도 하다. 이 두 번째 특성 때문에 원인 D(교정탭 재로드 폭주)가 "배치 직후"에는 상대적으로 덜 터지고, 사용자가 세션을 저장했다가 나중에 다시 열거나 다른 이미지를 몇 장 클릭한 뒤 교정탭에 들어가면 더 심하게 터진다.

### 개선안
`BatchProcess.run()`의 `processNext()` 안, 한 장의 분석이 끝나는 시점(`processed++` 직전)에 최근 N장만 남기고 해제:
```js
const KEEP_RECENT = 5;
if (processed - KEEP_RECENT >= 0) {
    const evictTarget = images[processed - KEEP_RECENT];
    if (evictTarget && evictTarget.imgElement && evictTarget._imgSrc) {
        evictTarget.imgElement.src = '';
        evictTarget.imgElement = new Image();
    }
}
```

**단, 이 개선을 원인 C·D 수정 없이 단독 적용하면 안 된다** — 아래 참조.

## 원인 B — 결과표(채점 탭) 렌더링이 매 조작마다 전체 재구성됨

(1차 분석과 동일, 요약만)

`scoring.js`의 `_renderOMR()`은 기본 83개 컬럼 × 962행 ≈ 8만 셀을 문자열로 통째로 이어붙여 `innerHTML`에 한 번에 주입한다. 정렬/필터/과목 변경 등 사소한 조작마다 전체를 처음부터 재생성한다.

**개선안**: 결과표 행 페이지네이션(100~150행/페이지). CSV/XLSX 내보내기는 영향 없음.

## 원인 C — 교정탭 썸네일이 "전체 해상도 진하기 처리"를 반복 실행함 (가장 심각·최우선)

### 위치
`correction.js` `_makeZoomCanvas()` (line 368~) → `canvas.js` `_getIntensifiedImage()` (line 677~)

### 문제
교정탭의 각 카드(수정중/이력)는 작은 썸네일(22~28px)을 그리기 위해:
```js
const intensified = CanvasManager._getIntensifiedImage(img); // 이미지 전체(2000×1550) 처리!
...
cvctx.drawImage(sourceImg, sx, sy, sw, sh, 0, 0, THUMB_SIZE, THUMB_SIZE); // 그 중 20px만 잘라씀
```
`_getIntensifiedImage()`는 이미지 **전체 해상도**에 대해 `getImageData` → 픽셀별 감마 LUT 적용 → `putImageData`를 수행한다 (`canvas.js:696~708`). 2000×1550px 기준 약 310만 픽셀을 매번 순회한다.

이 결과 캔버스는 `_intensityCache`에 캐싱되지만 **상한이 20개**(`canvas.js:711`)뿐이다. 교정탭 한 페이지에는 6개 컬럼 × 페이지당 30개 = 최대 180개의 카드가 표시되고(`PAGE_SIZE=30`), 이 카드들은 서로 다른 이미지에서 온 경우가 대부분이다 (오답/공란/중복이 여러 장에 흩어져 있음). **962장 규모에서는 페이지 하나에 20장보다 훨씬 많은 서로 다른 원본 이미지가 등장 → 캐시가 계속 밀려나며(LRU) 거의 매 카드마다 캐시 미스 → 전체 해상도 재처리가 반복된다.**

더 심각한 것은 이 렌더링이 **1회성이 아니라는 점**이다. `render()`는 다음마다 매번 새로 호출된다:
- 답안 하나 수정(Enter) → `setAnswerAndAdvance()` → `render()`
- "현재페이지 전체빈칸/전체확인" 버튼
- 페이지 이동(◀▶)

즉 채점자가 빈칸 하나를 고치고 Enter를 누를 때마다, 화면에 보이는 최대 180개 카드 중 캐시에서 밀려난 이미지 전부(수십~100장 이상일 수 있음)를 다시 통째로 재처리한다. 이미지 1장 처리에 수십ms만 잡아도 카드가 걸쳐있는 서로 다른 이미지가 80장이면 **한 번의 Enter 입력마다 수 초가 걸릴 수 있다.** 이것이 사용자가 "정말 심각하다"고 느끼는 지점의 실체로 보인다.

### 개선안
썸네일은 최종적으로 20~28px만 필요하므로, **이미지 전체를 처리할 필요가 없다.**
1. 먼저 원본에서 필요한 작은 영역(`sx, sy, sw, sh`)만 crop
2. 그 다음 크롭된 작은 캔버스(가로세로 수십px)에만 감마 LUT 적용

```js
// 전체 이미지 대신 crop 영역만 잘라서 그 위에 LUT 적용
const cropCanvas = document.createElement('canvas');
cropCanvas.width = sw; cropCanvas.height = sh;
const cropCtx = cropCanvas.getContext('2d');
cropCtx.drawImage(img.imgElement, sx, sy, sw, sh, 0, 0, sw, sh);
if (imgIntensity !== 100) {
    const imgData = cropCtx.getImageData(0, 0, sw, sh); // 수십×수십 픽셀 — 원본 대비 수천 배 저렴
    // LUT 적용 후 putImageData
}
```
이렇게 하면 픽셀 처리량이 "이미지 전체(310만 픽셀)"에서 "크롭 영역(보통 수백~수천 픽셀)"로 줄어 캐시가 없어도 사실상 병목이 아니게 된다. 이 수정이 **1000장을 한 번에 처리하기 위한 선행 조건**이다.

## 원인 D — 교정탭의 지연로드가 연쇄 재렌더 + 중복 로드를 유발

### 위치
`correction.js` `_makeZoomCanvas()` line 373~389, `imageManager.js` `ensureLoaded()` line 594~607

### 문제
카드에 필요한 이미지가 메모리에서 해제된 상태(`!img.imgElement.complete`)면:
```js
ImageManager.ensureLoaded(img).then((loaded) => {
    ...
    this.render(container); // 전체 교정탭을 통째로 재렌더!
});
```
- **재로드 1건 완료 → 교정탭 전체(최대 180개 카드) 재렌더** → 그 재렌더 안에서 아직 안 끝난 다른 이미지들에 대해 또 `ensureLoaded()`를 호출
- `ensureLoaded()`는 이미 로딩 중인지 확인하지 않고 **매번 새 `Image()` 객체를 만들어 다시 로드를 시작**한다 (`imageManager.js:602`: `const newImg = new Image();`). 즉 같은 이미지에 대해 재렌더가 여러 번 겹치면 **같은 파일을 중복으로 디코딩**한다.
- 결과: 이미지가 N장 해제돼 있으면 최악의 경우 "이미지 로드 완료 → 전체 재렌더 → 다음 이미지 로드 트리거"가 N번 연쇄되고, 그 사이 일부는 중복 로드까지 겹친다.

`render()` 안에 `_renderGen`으로 stale 콜백을 걸러내는 안전장치는 있지만, 이는 "오래된 렌더의 콜백을 무시"할 뿐 "재렌더 자체가 연쇄되는 구조"는 막지 못한다.

### 원인 A와의 상호작용 (★ 반드시 확인해야 하는 부분)
지금은(원인 A 미수정) 배치가 끝나면 대부분 이미지가 로드된 채로 남아있어 이 문제가 상대적으로 덜 드러난다. **그런데 원인 A의 "배치 중 최근 5장만 남기고 해제" 수정을 그대로 적용하면, 배치가 끝난 시점에 962장 중 957장이 이미 해제된 상태가 된다.** 이 상태로 교정탭을 열면 원인 D의 연쇄 재렌더 + 중복 로드가 지금보다 훨씬 크게(거의 전체 이미지 대상으로) 발생한다.

**즉 원인 A만 고치고 D를 고치지 않으면, "배치 중 부하"는 줄어들지만 "교정탭이 훨씬 더 느려지는" 회귀가 생긴다.** 사용자가 "그거에 따라 다른 기능에 문제가 없을지 확인해야 한다"고 지적한 부분이 정확히 이 지점이다.

### 개선안
1. **전체 재렌더 대신 카드 단위 갱신**: 이미지 로드가 끝나면 `this.render(container)` 전체 재호출 대신, 해당 카드의 DOM 요소만 찾아 썸네일을 교체 (예: 카드에 `data-img-idx` 부여 → 로드 완료 시 해당 카드만 다시 그림)
2. **중복 로드 방지**: `ImageManager`에 이미지별 "로딩 중인 Promise" 캐시를 두고, 이미 로딩 중이면 새 `Image()`를 또 만들지 않고 기존 Promise를 재사용
   ```js
   _loadingPromises: new Map(),
   ensureLoaded(imgObj) {
       if (imgObj.imgElement && imgObj.imgElement.complete && imgObj.imgElement.width > 0) {
           return Promise.resolve(imgObj.imgElement);
       }
       if (this._loadingPromises.has(imgObj)) return this._loadingPromises.get(imgObj);
       const p = new Promise((resolve) => { ... });
       this._loadingPromises.set(imgObj, p);
       p.finally(() => this._loadingPromises.delete(imgObj));
       return p;
   }
   ```

원인 C(크롭 후 처리)가 적용되면 픽셀 처리 비용은 사라지지만, "이미지가 아예 메모리에서 해제된 경우" 재로드 자체는 여전히 필요하다 — 이 재로드 폭주를 막는 것이 원인 D 수정의 역할이다.

## "1000장을 한 번에 다 처리할 수 있는가?" — 결론

**가능하다. 단, 아래 순서를 반드시 지켜야 한다.**

| 순서 | 수정 | 이유 |
|---|---|---|
| ① | 원인 C 수정 (교정탭 썸네일: crop 먼저, LUT는 crop 영역에만) | 이게 없으면 이미지가 로드돼 있어도 교정탭이 느림. 가장 시급 |
| ② | 원인 D 수정 (카드 단위 갱신 + 중복 로드 방지) | 이게 없으면 원인 A 수정 후 교정탭이 지금보다 더 느려짐 |
| ③ | 원인 A 수정 (배치 중 이미지 순차 해제) | ①②가 끝난 뒤에 적용해야 안전 — 배치 메모리 문제 해결 |
| ④ | 원인 B 수정 (결과표 페이지네이션) | 독립적, 아무 때나 적용 가능 |

①②를 먼저 하지 않고 ③(원인 A)만 적용하면: 배치 메모리는 고정되지만 교정탭은 "지금보다 더" 느려진다 — 사용자가 우려한 정확히 그 시나리오. 따라서 **작업 순서를 C → D → A → B로 재조정**한다.

---

## 영향 범위 / 리스크

- **원인 C 수정**: 화면에 보이는 썸네일 픽셀 결과는 동일(짤린 영역에 동일한 LUT 적용), 시각적 차이 없음. 리스크 낮음.
- **원인 D 수정(카드 단위 갱신)**: 카드 DOM 구조에 식별자를 추가해야 해서 `_renderItem`/`render()` 코드 변경 범위가 원인 C보다 조금 큼. 페이지 이동/필터 등 "전체가 바뀌어야 하는" 경우엔 여전히 전체 재렌더가 맞으므로, "이미지 지연로드 완료" 콜백에서만 부분 갱신으로 바꾸는 좁은 범위의 수정.
- **원인 A 수정**: 배치 중 오류 이미지 재확인 시 재로드 지연(수십ms) 발생 — 원인 C·D가 먼저 적용된 상태라면 이 재로드가 가볍고(크롭만 필요하면 재로드 자체가 아예 필요 없을 수도 있음) 카드 단위 갱신이라 체감 영향 적음.
- **원인 B 수정(페이지네이션)**: 표를 스크롤로 쭉 보던 기존 UX가 "페이지 이동" 방식으로 바뀜.

## 요약

1. 배치 중 메모리 누적(원인 A)과 결과표 렌더링 지연(원인 B)은 1차 분석 그대로 유효.
2. 이번 점검에서 교정탭이 "정말 심각하게" 느린 진짜 원인을 찾음: 썸네일 하나 그리자고 이미지 전체 해상도를 재처리하는 구조(원인 C) + 지연로드 완료마다 전체를 다시 그리며 중복 로드까지 겹치는 구조(원인 D).
3. 원인 A(배치 중 이미지 해제)를 원인 C·D보다 먼저 적용하면 교정탭이 지금보다 더 느려지는 회귀가 생긴다 — 반드시 **C → D → A → B** 순서로 진행.
4. 이 순서를 지키면 1000장을 한 세션에서 한 번에 올리고 일괄분석 + 교정 + 결과표 확인까지 전부 문제없이 처리 가능하다.
