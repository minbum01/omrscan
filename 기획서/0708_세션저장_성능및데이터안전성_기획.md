## 원인 E — 세션 저장 시 이미지 전체를 한 번에 인코딩 + 단일 IPC 전송 (크래시 유력 원인)

### 위치
`session.js` `saveCurrentSession()` (line 803~), `main.js` `ipcMain.handle('session:save', ...)` (line 200~)

### 현재 동작
```js
// session.js — saveCurrentSession()
const dirtyItems = isFirstSave ? allItems : allItems.filter(item => item.imgObj._imgDirty);
imageDataArr = [];
for (let i = 0; i < dirtyItems.length; i++) {
    ...
    const c = document.createElement('canvas');
    c.width = saveImg.imgElement.naturalWidth; c.height = saveImg.imgElement.naturalHeight;
    c.getContext('2d').drawImage(saveImg.imgElement, 0, 0);
    imageDataArr.push({ filename: saveName, dataUrl: c.toDataURL('image/jpeg', 0.9) }); // base64 인코딩
}
...
const result = await window.electronAPI.saveSession(name, data, imageDataArr); // ★ 한 번에 전부 전송
```

1. 저장 대상 이미지(최초 저장 시 전체, 이후엔 변경분만)를 **순서대로 base64 JPEG 문자열로 인코딩**해 `imageDataArr` 배열 하나에 전부 모은다.
2. 다 모은 뒤 **단 한 번의 `ipcRenderer.invoke('session:save', ...)` 호출**로 렌더러 → 메인 프로세스에 전체 배열을 통째로 전송한다.

### 규모 추정
- 원본 스캔본 3300×2550 → `MAX_SIZE=2000`으로 리사이즈된 이미지 기준 약 2000×1550px
- JPEG 품질 0.9로 인코딩 시 파일당 대략 300KB~1MB, **base64 인코딩 시 원본 대비 약 1.37배 문자열 크기**
- 962장을 최초 저장(전체 대상)하면 `imageDataArr`에 **약 400MB~1.3GB 규모의 문자열**이 동시에 쌓임
- 이 배열 전체가 Electron IPC의 구조적 복제(structured clone)로 렌더러→메인 프로세스에 복제되며 전송 — 이 순간 양쪽 프로세스에 동시에 큰 메모리 사본이 생김
- 여기에 원인 A(배치 중 이미지 순차 해제)가 적용된 상태라면, 저장 시점에 대부분 이미지가 evict돼 있어 `ensureLoaded()`로 **다시 로드해야 하는 이미지 수도 늘어남** → 저장 시간이 더 늘어남

**"크러쉬나서 꺼진거 같아"의 유력 후보가 바로 이 지점이다.** 특히 최초 저장(첫 세션 저장, 이미지 원본을 처음 디스크에 쓰는 시점)은 항상 전체 이미지를 대상으로 하므로 962장 규모에서 가장 위험하다.

### 개선안 — 청크 단위 저장
전체를 한 번에 모으지 않고, **N장(예: 30장)씩 끊어서 여러 번 IPC 호출**한다.

```js
// session.js (개선안)
const CHUNK = 30;
for (let start = 0; start < dirtyItems.length; start += CHUNK) {
    const chunk = dirtyItems.slice(start, start + CHUNK);
    const chunkData = [];
    for (const { imgObj, filename } of chunk) {
        // ... ensureLoaded + canvas + toDataURL ...
        chunkData.push({ filename, dataUrl });
    }
    await window.electronAPI.saveSessionImagesChunk(name, chunkData); // 청크 단위 IPC
    // chunkData는 다음 루프 진입 전에 GC 대상이 됨 — 메모리 상한이 "청크 크기"로 고정
}
```
메타데이터(JSON)와 "정리(cleanup)"는 별도의 단일 호출로 먼저 처리(아래 원인 F 개선안과 함께 처리).

이렇게 하면 메모리 사용량 상한이 "전체 이미지 수"가 아니라 "청크 크기(30장) × 이미지당 용량" 수준으로 고정되고, 체감 저장 속도도 개선된다 (진행률 표시도 청크 단위로 더 세밀하게 가능).

## 원인 F — 부분 저장 시 "정리(cleanup)" 로직이 변경 안 된 이미지 파일까지 삭제 (별개의 데이터 유실 버그)

### 위치
`main.js` `ipcMain.handle('session:save', ...)` line 216~244

### 문제
```js
// main.js
const keepSet = new Set(images.filter(i => i && i.filename).map(i => i.filename...));
// 이전에 있던 파일 중 이번 저장에 없는 것은 삭제
fs.readdirSync(imgDir).forEach(f => {
    if (!keepSet.has(f)) { try { fs.unlinkSync(path.join(imgDir, f)); } catch (_) {} }
});
```
`images`(= `imageDataArr`)는 **최초 저장 이후에는 "이번에 변경된(dirty) 이미지만"** 담고 있다 (`session.js:966`: `dirtyItems = isFirstSave ? allItems : allItems.filter(item => item.imgObj._imgDirty)`). `_imgDirty`는 신규 업로드 또는 회전/기울기 보정 시에만 `true`가 된다 (`canvas.js:777, 893`, `imageManager.js:108`).

→ **최초 저장 이후, 예를 들어 962장 중 5장만 기울기 보정하고 저장하면, `keepSet`에는 그 5장만 들어가고, 나머지 957장은 "이번 저장에 없는 파일"로 간주되어 디스크에서 전부 삭제된다.**

이건 메모리·속도와 무관한 **순수 데이터 유실 버그**다. 현재는 "최초 저장은 항상 전체 이미지 대상"이라 최초 저장 직후 바로는 드러나지 않지만, 이후 부분 수정 후 저장하는 일상적인 흐름에서 언제든 터질 수 있다.

### 개선안
"삭제 대상 판단"과 "이미지 데이터 전송"을 분리한다.
1. `saveCurrentSession()`에서 **이번 세션에 존재해야 할 전체 파일명 목록**(`allItems.map(...)`, dirty 여부 무관)을 만들어 메타데이터 저장 호출에 함께 전달
2. `main.js`의 `session:save` 핸들러는 이 **전체 파일명 목록**을 기준으로 `keepSet`을 만들어 정리(cleanup)하고, 실제 이미지 바이트 쓰기는 이후 청크 IPC 호출들이 담당
3. 청크 IPC 호출(`session:save-images-chunk`)은 정리 로직 없이 **파일 쓰기만** 수행

```js
// main.js (개선안 스케치)
ipcMain.handle('session:save', async (event, sessionName, data, expectedFilenames) => {
    // JSON 저장 (기존과 동일)
    ...
    if (expectedFilenames) {
        const keepSet = new Set(expectedFilenames.map(f => f.replace(/[\\/:*?"<>|]/g, '_')));
        fs.readdirSync(imgDir).forEach(f => { if (!keepSet.has(f)) fs.unlinkSync(...); });
    }
    return { success: true, path: filePath };
});

ipcMain.handle('session:save-images-chunk', async (event, sessionName, images) => {
    // 정리 없이 파일만 씀
    images.forEach(img => { /* base64 → 파일 쓰기 */ });
    return { success: true };
});
```

## 구현 순서 제안 (이 문서 범위)

| 단계 | 작업 | 파일 | 목적 |
|---|---|---|---|
| 1 | `session:save`에서 "정리(cleanup)" 로직을 전체 파일명 목록 기준으로 분리 | `main.js`, `session.js` | 원인 F(데이터 유실 버그) 제거 — 가장 먼저, 안전 최우선 |
| 2 | 이미지 저장을 청크(30장) 단위 IPC로 분할 | `session.js`, `main.js` | 원인 E(메모리 폭증·크래시) 해소 |
| 3 | 세션 불러오기(`session:load`)는 이미 `file://` URL 방식이라 안전 — 추가 조치 불필요 (점검 결과만 기록) | - | - |

**F를 E보다 먼저 고치는 이유**: E(청크 저장)를 구현하려면 어차피 "정리 로직 분리"가 선행돼야 하고(청크 단위로는 keepSet을 매번 새로 만들 수 없으므로), F는 이미 지금 이 순간에도 터질 수 있는 활성 버그라 우선순위가 더 높다.

## 선행 문서(A·B·C·D)와의 관계

`0708_대용량배치_성능개선_기획.md`에서 정리한 원인 A(배치 중 이미지 순차 해제)는 이미 새 폴더에 적용돼 있다. 이 상태에서 세션을 저장하면, 저장 시점에 대부분 이미지가 evict돼 있어 `ensureLoaded()` 재로드가 늘어나 저장이 더 오래 걸릴 수 있다 — 원인 E(청크 저장)를 적용하면 재로드도 청크 단위로 분산되어 이 영향이 줄어든다.

**전체 작업 순서 (누적)**: C → D → A → B (완료, 새 폴더 적용됨) → **F → E (이번 문서, 다음 작업)**

---

## 영향 범위 / 리스크

- **원인 F 수정**: cleanup 판단 기준이 바뀌므로, 세션 폴더에 수동으로 넣어둔 이미지가 있다면(비정상 케이스) 다음 저장 시 정리될 수 있음 — 정상 사용 흐름에서는 영향 없음.
- **원인 E 수정(청크 저장)**: IPC 호출 횟수가 늘어나지만(30장당 1회, 962장이면 약 32회) 각 호출이 훨씬 가벼워 총 소요 시간은 오히려 줄어들 가능성이 높음. 저장 중 진행률 표시도 더 세밀해짐.
- 두 수정 모두 디스크 쓰기 로직이라 실제 대량 이미지(언어_통합/추리_통합 962장)로 저장→종료→재시작→불러오기까지 전체 왕복 테스트가 필요함 — 새 폴더(성능개선 개발용)에서만 검증 후 원본에 반영.

## 결론

세션 저장은 배치분석과 별개의 독립적인 문제였고, 훨씬 심각하다 — 방금 겪은 크래시의 유력 원인(원인 E)이자, 크래시가 없어도 언제든 이미지 파일이 통째로 삭제될 수 있는 기존 버그(원인 F)까지 포함한다. **F(정리 로직 분리) → E(청크 저장)** 순서로 고치는 것을 제안한다.
